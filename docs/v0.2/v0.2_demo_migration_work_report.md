## 2. 新增的程式責任

### 2.1 JSON Serializer

位置：`Assets/JobCheck/Persistence/Storage/PersistenceJsonSerializer.cs`

責任：

- 將簡單 DTO 轉成 UTF-8 JSON。
- 將 JSON 還原成指定 DTO。
- 錯誤 JSON 回傳失敗資訊，不讓例外直接穿透到 UI。
- 不依賴 `UnityEngine`，可在 EditMode 與一般 .NET 測試環境執行。

它只處理 JSON 語法和 DTO 形狀，不判斷公司名稱、外鍵或求職狀態是否合理。

### 2.2 JobCheckDataRepository

位置：`Assets/JobCheck/Persistence/Storage/JobCheckDataRepository.cs`

責任：

- 從 `data/companies`、`data/jobs`、`data/applications` 載入完整資料集。
- 使用既有 Mapper 將 DTO 轉成 Domain。
- 執行 Company 必要欄位、各模型 Validator 與 `JobCheckDataSetValidator`。
- 錯誤包含檔案、欄位路徑、錯誤代碼與訊息。
- 任何檔案失敗時不回傳可被誤用的半套資料。
- 讀取不存在的目錄時不會建立任何檔案。
- 寫入完整快照時只接受不存在或完全空白的目錄，不覆蓋既有資料。
- 所有 DTO 都先成功轉換與序列化後，才開始建立輸出檔案。
- 單檔先寫同目錄暫存檔，再以 rename 產生正式檔案。

目前的 `WriteSnapshot` 是 migration staging 用途，不是日常新增／編輯單筆資料的最終 API。

### 2.3 V0.1 Demo Migration

位置：`Assets/JobCheck/Persistence/Migration/JobCheckV01Migration.cs`

責任：

1. 確認來源目錄存在。
2. 只接受 `schema_version: 0.1` 與 `source.platform: demo`。
3. 掃描來源並計算檔案大小與 SHA-256。
4. 完整備份 `jobs`、`job_tracking`、`job_index`。
5. 依正規化公司名稱合併 Company。
6. 保留舊 JobPosting ID，並產生穩定的 Company/Application/Event UUID ID。
7. 將 tracking 轉成最多一筆 Application 與 MigrationSnapshot。
8. 先寫入獨立 staging。
9. 用正式 Repository 把 staging 全部重新讀回並驗證。
10. 全部成功後才將 staging 目錄一次切換成正式 `data`。

重跑相同正式目標時會回報 `TargetAlreadyExists`，不覆蓋、不產生第二套 Application。

## 3. Migration 規則落實

### 公司

- 名稱只做 Unicode Form C、前後空白移除與連續空白合併。
- 正規化後完全同名才共用 Company。
- 不做模糊比對、別名猜測或 AI 合併。
- Company ID 由 migration version 與正規名稱產生穩定 UUID；不同次獨立 migration 仍會得到相同 ID。
- ID mapping 寫入 manifest。

### 職缺

- 保留 `demo_job_###` 舊 ID，避免不必要的關聯變動。
- 公司名稱不重複存入 JobPosting；使用 `company_id` 連結正式 Company。
- 薪資、地點、工時、需求、福利與流程轉入對應 Domain 子物件。
- 舊 ID 同時保留在 `legacy_id` 供追查。

### Application

- `not_viewed`、`not_applied` 若沒有真實使用者內容，不建立 Application。
- `interested` 轉成 `saved`。
- `waiting_reply` 轉成 `waiting_response`。
- `interviewing` 依舊 UI 語意轉成 `interview_completed`。
- `not_applying`、`closed` 轉成 `closed_by_candidate`，原因使用 `other` 並留下 migration 說明。
- 不完整的 `archived` 類狀態不直接封存，使用 `unknown + needs_review`。
- 獨立 `job_tracking` 檔存在時優先於職缺內嵌 tracking，符合目前 V0.1 UI 的實際資料來源。

### 事件

- 舊資料只有目前狀態，不能展開成多筆假歷史。
- 每個轉換出的 Application 只建立一筆 `migration_snapshot`。
- `source_reference` 保存為相對路徑，例如 `job_tracking/demo_job_001.tracking.json`，不綁定某台電腦的使用者目錄。
- ID 使用穩定 UUID，manifest 內保存 mapping。

## 4. 安全措施與證據

| 風險 | 防護 |
|---|---|
| 讀取時意外建立 tracking | Repository 的 Load 只有讀取，NotFound 不建立目錄或檔案 |
| 壞 JSON 造成整批清空 | 任一檔案失敗即整批失敗，Value 不可使用 |
| 未知版本被當成新版 | 只接受 V0.2 Repository schema；migration 只接受 V0.1 |
| 真實平台資料誤進第一輪 | migration 強制 platform 必須是 `demo` |
| ID 被當成路徑 | 寫入前拒絕分隔符、`..` 與無效檔名字元 |
| Application 與事件只寫一半 | Event 內嵌 Application JSON，同一檔案一起寫入 |
| migration 中途失敗污染正式資料 | 備份與輸出都在 work/staging；驗證後才 rename 成正式 data |
| 重跑產生重複資料 | 正式 data 有內容即拒絕；migration ID 亦為穩定產生 |
| 舊資料被改動 | 41 個來源檔案的 migration 前後 SHA-256 全部一致 |
| 不同電腦路徑失效 | Domain 事件只保存相對 source reference |

## 7. 為什麼需要這樣設計

如果被問到，可以用下面的短版回答：

> V0.1 的 UI 直接讀寫 JSON，而且列表讀取會自動建立 tracking。V0.2 把讀寫集中到 Repository，先把 JSON 轉成 DTO，再由 Mapper 轉成有規則的 Domain；migration 只在 staging 工作，完整驗證後才切換。這樣可以避免壞資料、半套寫入與讀取副作用，也能證明舊資料沒有被偷偷修改。

各層存在的原因：

| 層 | 簡單說法 |
|---|---|
| Legacy DTO | 看得懂舊 V0.1 JSON，但不讓舊格式污染新版模型 |
| V0.2 DTO | 描述新版 JSON 要長什麼樣子 |
| Mapper | 明確翻譯 DTO 與 Domain，不把格式細節塞進業務物件 |
| Domain／Validator | 判斷資料在求職規則上是否合理 |
| Repository | 集中管檔案、錯誤、安全寫入與完整資料驗證 |
| Migration | 一次性的舊資料搬運流程，包含備份、manifest、report 與 staging |

## 9. 已知限制

1. 現有 Unity UI 仍走 V0.1 路徑，因此 `data/` 已可安全載入，但目前畫面不會使用它。
2. Repository 的完整快照寫入只允許空目錄；日常編輯所需的單筆交易 API 尚未建立。
3. V0.2 JSON 目前是單行 compact JSON，適合機器處理，但人工閱讀不如 pretty JSON。
4. Company 必要欄位驗證目前由 Repository 執行，尚無獨立 `CompanyValidator`。
5. 第一輪只接受 demo，刻意拒絕任何非 demo 平台資料。
6. Build 與 Play Mode 尚未驗證；本批次只驗證純 C# assembly 與 EditMode tests。
